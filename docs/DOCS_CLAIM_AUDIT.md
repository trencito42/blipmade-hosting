## What the platform really does (the areas that usually carry false promises)

### The applications and databases that can actually be deployed

The catalog of the platform holds **five** products (`api/prisma/seed.ts:55-178`): `wordpress`, `code-server`, `discord-bot`, `uptime-kuma`, `postgresql`. All five are `visible: true` with an active MONTHLY/EUR price (`api/prisma/seed.ts:210-212`), so all five appear in the public catalog (`api/src/routes/catalog.ts:165-176`).

Only **one** of them can be ordered. `discord-bot` is the only product with an egg, an image and `deployable: true` — egg 15, the verified Node.js image (`api/prisma/seed.ts:105-128`). The other four carry `eggId: null`, `dockerImage: null`, `deployable: false` and the description *"Its image is not installed on the platform yet, so it is listed but cannot be deployed"* (`api/prisma/seed.ts:57-78, 81-102, 131-152, 155-176`). `deploymentAvailability()` turns that into the state `COMING_SOON` with the blocker *"It has not been validated for deployment yet"* (`api/src/services/availability.ts:93-113`).

Seven of the twelve documented apps — **ghost, forgejo, grafana, n8n, mysql, redis, mongodb** — are not in the catalog at all. Their documentation pages are never published, because `availablePages()` only publishes a page for a product the catalog offers (`web/src/pages/Docs.tsx:2243-2250`). They are dead content in the source file that the rebuild must not resurrect.

### One-click provisioning

There is **no one-click install of an application**. On deploy the platform writes three files into the container — `package.json`, `index.js`, `README.md` — where `index.js` is a ~30-line Node.js HTTP server that answers on the health path of the product (`api/src/services/starter-apps.ts:84-160`, `api/src/services/provisioning.ts:301-345`). The real, unmocked test `api/tests/starter-app.test.ts:36-89` asserts exactly that. The health probe comes from `product.healthProbe` in the database, default path `/` (`api/src/services/provisioning.ts:770-788`). **Every documented first-run installer (WordPress, Ghost, Forgejo, code-server, Grafana, n8n, Uptime Kuma, MySQL, Redis, MongoDB, PostgreSQL) therefore never happens.**

### Environment variables

The platform sets **no application variable**. The container application reads `SERVER_PORT` and `PORT` (`api/src/services/starter-apps.ts:77-82`); the only variable a seeded product declares is `MAIN_FILE` for the Node.js egg (`api/prisma/seed.ts:126`). Every variable in the documented tables is written by the customer, through `PUT /instances/:id/startup` (`api/src/routes/instance-server.ts:864-921`). The environment lives in the server of the panel, is read back in plain text by the owner (`api/src/routes/instance-server.ts:847-855`) and is visible to everything that runs in the container. **Saving the environment does not restart the instance** — the route writes the values and returns (`api/src/routes/instance-server.ts:864-910`, `api/src/services/pterodactyl/application.ts:208-231`); the new values apply at the next start.

### Startup commands and versions

The only startup command that exists in the product data is `npm run start` on the verified Node.js egg (`api/prisma/seed.ts:123-126`). The customer can change it (`api/src/routes/instance-server.ts:840-921`). No product ships an application version, and the platform never patches an application in place. The container gets **no restart policy** from the platform, so a process that dies is not brought back by the platform.

### Resource limits and minimums

The minimums of the catalog are, in MB of memory and GB of disk: `wordpress` 512/5, `code-server` 1024/5, `discord-bot` 256/1, `uptime-kuma` 256/5, `postgresql` 1024/5 (`api/prisma/seed.ts:63-176`; the label turns MB into GB in `web/src/lib/pricing.ts:213`). The configurator refuses anything outside the minimum and the maximum of the product (`api/src/services/pricing.ts:141-153`) — and **nothing else**: there is no check against the data that is on the disk, so the documented "a disk cannot shrink below your files" does not exist.

### Resizing and upgrading

A resize updates the build limits of the **same** server; the files, the environment and the address stay (`api/src/services/pterodactyl/application.ts:147-197`, `api/src/routes/instance-server.ts:713-735`). No restart is issued. A change that costs **more** is not applied: the quote sets `requiresPayment` (`api/src/services/upgrades.ts:204-211`), the route creates an `UPGRADE` order and returns a checkout (`api/src/routes/instances.ts:305-345`), and the change is applied only after the payment is confirmed (`api/tests/upgrades.test.ts:122, 148`). Only a change that costs less is applied at once and credited on the next invoice (`api/src/services/upgrades.ts:415`, `api/src/services/billing.ts:212-215`).

### Backups — the two different things

**1. The customer backup** (`api/src/routes/instance-server.ts:593-709`, `api/src/services/panel/operations.ts:226-244`, tab `web/src/app/instance/BackupsTab.tsx`): the customer asks for it, the **panel** writes an archive of the **files of the container** **on the node**; it is downloadable as `.tar.gz` and restoring it **replaces the files of the container** with the archive. It is **manual only** — there is no schedule. It holds no dump of a database that runs elsewhere, and the platform keeps no time limit of its own: the number of backups is the limit of the egg of the panel (`feature_limits.backups`, `api/src/services/pterodactyl/types.ts:34, 109`). The dashboard already offers it (`BackupsTab.tsx:25, 141-176`) and **the documentation never mentions it**.

**2. The platform backup** (`scripts/backup.sh:1-40, 62-96`): the operator's own backup of the **platform's** PostgreSQL database, its configuration and the uploads of the customers, written by cron into `BACKUP_DIR`, kept `BACKUP_KEEP_DAYS` (default 14) days, with an optional off-site copy (`scripts/backup-offsite.sh`). It says nothing about the data of a customer and is not a customer feature.

**The documentation conflates nothing explicitly — it mentions neither — but it claims the opposite of the truth.** The sentences *"Blipmade does not take automatic backups of your data yet"*, *"Blipmade does not back them up for you yet"* and *"Blipmade does not back up either of them for you yet"* read as if the platform holds no copy of the customer's files, while the panel backup of the customer exists, and while a second, unrelated backup system (the platform's own) is easy to mistake for it. The first half of the sentence is true: there is no **automatic** backup. The rebuild must document the manual backup, what it holds, where it lives, how it is restored and what it does **not** cover.

### SSH, SFTP and file access

There is **no SSH and no SFTP** anywhere in the platform: the strings `ssh` and `sftp` do not occur in `api/src` or `web/src` at all, except in the keyword list of the documentation itself (the only other hit in the repository is the fake `ssh` binary that the off-site backup drill installs for the operator, `api/tests/backup-offsite-drill.test.ts:133`). The customer reaches the instance through the **file browser** (`api/src/routes/instance-server.ts:163-446`), the **console** (`api/src/routes/instances.ts:221-252`) and the **panel of the instance**. The Forgejo answer *"Instances are reached over HTTP and HTTPS. Use the HTTPS clone URL"* is the only honest statement about it.

### Domains and SSL

Ownership is proven with a **TXT** record that carries a random token of 24 characters per hostname (`api/src/routes/domains.ts:293-296`); an A record never proves anything (`api/src/routes/domains.ts:37-43`). The gateway **refuses to route a hostname that was never proven** (`api/src/services/gateway.ts:310-312`), and a claim that is never proven **expires after seven days**, after which the hostname is free again (`api/src/routes/domains.ts:45-46, 195-204, 406-408`). **Nobody issues a certificate:** the route the platform writes into Caddy is a plain `reverse_proxy` with no TLS policy (`api/src/services/gateway.ts:254-265`) and there is no ACME/Let's Encrypt client in `api/src`; the edge Caddyfile only covers the platform's own domain (`deploy/edge/Caddyfile:55-90`). The customer hostname is therefore served **over plain HTTP**. The `ssl` page is honest about the absence of certificates, but its advice to "terminate TLS at your own DNS provider" is wrong, because the platform-managed hostname has no TLS at all.

### Payment methods, currency and billing cycles

The platform bills **monthly in euros** (`api/prisma/seed.ts:212`, `api/src/routes/catalog.ts:130`) and has **no setup fee** (no such field in `ProductPrice` or `Order` in `api/prisma/schema.prisma`). The card is collected in a session of the provider (`api/src/services/stripe.ts:931-936`).

**The platform currently takes no real payment.** `PAYMENTS_ENABLED` defaults to `false` (`api/src/env.ts:152`) and is `false` in `.env`; `paymentsEnabled` also needs a Stripe secret key (`api/src/env.ts:413`). The key in `.env` is a **test key** (`sk_test…`), and `STRIPE_TEST_MODE=false` with `NODE_ENV=production` turns the local test gateway off (`api/src/services/stripe.ts:45-55`). The consequence: `paymentState()` answers *"Payments are not available at the moment: payments are turned off on this environment"* (`api/src/services/stripe.ts:99-117`), the checkout creates no session and `POST /billing/payment-method` throws `payments_unavailable` (`api/src/services/stripe.ts:922-926`). **No documentation may imply that a card is charged or that an invoice is paid.**

### Refunds and cancellation

Cancelling sets `cancelAtPeriodEnd` and leaves the instance running (`api/src/routes/instances.ts:393-422`). At the end of the paid period the instance is **stopped**, the data of the customer is **exported**, and the service is **kept for the retention term — 30 days by default** (`api/src/services/billing.ts:78, 580-631, 708-741`). The deletion only runs when the operator has switched the auto-delete on, and that switch is **off by default** (`api/src/services/billing.ts:440-447`). So the data is **not** removed at the end of the period. There is **no customer-facing refund route**: refunds happen only through the operator (`api/src/routes/admin.ts:600`), a refused paid plan change (`api/src/services/upgrades.ts:415`) or a failed provisioning (`api/src/services/provisioning.ts:1187`); the platform's own refund policy lists exactly those two automatic cases (`web/src/legal/documents/refund.tsx:65-86`).

### Email hosting

The feature exists and is complete: domains, mailboxes, aliases, forwarding, quotas, the DNS state, suspension, cancellation and reactivation (`api/src/services/mail.ts:238-706`, `api/src/routes/mail-commerce.ts:149-398`; the plans carry 1-3 domains, 2-10 mailboxes, 20-100 aliases and a send limit of 100-500 per interval, `api/src/lib/mail-plan-drafts.ts:74-116`). **It is not sold:** `MAIL_SALES_ENABLED` defaults to `false` (`api/src/env.ts:225`) and is `false` in `.env`; `deploymentAvailability()` then answers *"Hosted mail is not on sale at the moment"* (`api/src/services/availability.ts:99-104`). The documentation says nothing about mail at all.

### User permissions and security

A customer owns its instances, domains, tickets, subscriptions and files; every route checks the owner (`api/src/routes/instance-server.ts`, `api/src/routes/domains.ts:280-284`). Sessions live in an `HttpOnly` cookie (`api/src/plugins/auth.ts:254-262`), every writing request needs the `X-CSRF-Token` header against the readable `bm_csrf` cookie (`api/src/plugins/csrf.ts:34`), the account keeps at most 20 sessions (`api/src/plugins/auth.ts:132`) and the account can close them one by one (`api/src/routes/settings.ts:533-557`). Staff is separate: `ADMIN` holds every permission, `STAFF` only the ones that were granted (`api/src/lib/permissions.ts:2-52`).

### Suspension and retention

A failed payment makes the subscription `PAST_DUE` (`api/src/services/billing.ts:836`); after a grace of **7 days** (`api/src/services/billing.ts:49`) the instance is stopped and marked `SUSPENDED` (`api/src/services/billing.ts:1548-1560`). **The data is kept.** A cancelled service is kept for the retention term of 30 days by default (`api/src/services/billing.ts:78, 592`), the deletion runs only when the operator enables it (`api/src/services/billing.ts:447`), and the customer data is exported before anything is deleted (`api/src/services/billing.ts:573-631`).

### Availability and product status

There is **no uptime SLA and no availability percentage anywhere in the product**. The platform's own service level page says so explicitly: *"The platform does not publish an availability figure and does not guarantee that the service will be reachable at any given moment. There is no service credit"* (`web/src/legal/documents/sla.tsx:41-46`), and the status page says *"90-day uptime history is not available yet"* (`web/src/pages/Status.tsx:242`). **The documentation makes no such promise today** — the only occurrences of "uptime" in `Docs.tsx` are the product name Uptime Kuma. Any promise of one must be reported as `MISLEADING`; there is none to remove, and the rebuild must not add one.
